## 1. Оформление и оплата

```mermaid
sequenceDiagram
    actor Buyer as Покупатель
    participant API as Web / Gateway
    participant Orders as Orders
    participant Catalog as Catalog
    participant Broker as RabbitMQ
    participant Payments as Payments
    participant PSP as Платёжный провайдер
    participant Notify as Notifications
    Buyer->>API: Оформить заказ, Idempotency-Key
    API->>Orders: Создать заказ (товары и количества)
    Orders->>Catalog: Проверить публикацию, получить цены и seller_id
    Catalog-->>Orders: Актуальные карточки
    Note over Orders: Одна локальная транзакция:<br/>заказ PendingPayment, снимки, сумма, outbox
    Orders-->>API: 201, order_id, PendingPayment
    API-->>Buyer: Заказ создан, платёж подготавливается
    Orders-->>Broker: OrderPlaced; OrderStatusChanged
    Broker-->>Payments: OrderPlaced
    Payments->>PSP: Создать платёж, стабильный idempotency key
    PSP-->>Payments: payment_id, checkout_url
    API->>Payments: Прочитать состояние попытки по order_id
    Payments-->>API: checkout_url или Preparing
    API-->>Buyer: Переход к оплате
    Buyer->>PSP: Оплата на странице провайдера
    PSP->>API: Подписанный webhook
    API->>Payments: Передать исходное тело и подпись
    Note over Payments: Проверка подписи, суммы, валюты и повтора.<br/>Операция, учёт и outbox в одной транзакции
    Payments-->>Broker: PaymentSucceeded
    Broker-->>Orders: PaymentSucceeded
    Note over Orders: Заказ Paid и outbox в одной транзакции
    Orders-->>Broker: OrderStatusChanged(Paid)
    Broker-->>Notify: OrderStatusChanged(Paid)
    Note over Notify: Уникальное задание отправки<br/>и передача email/SMS-провайдеру
```

HTTP-ответ `201` означает, что заказ записан, а не оплачен. Подготовка ссылки оплаты асинхронная: пока её нет, интерфейс показывает `Preparing` и ограниченно опрашивает Payments через Gateway с backoff. Ошибка или недоступность провайдера не превращается в ложный успех.

Orders доверяет цене Catalog в момент серверной проверки и сохраняет снимок. В проекте принято, что цена этого снимка действует на срок оплаты заказа, даже если продавец позже меняет каталог. Это явная политика фиксации цены, а не распределённая блокировка. Если карточка недоступна уже при проверке или Catalog не отвечает, заказ не создаётся; возвращается ошибка валидации либо временная недоступность.

После успешной оплаты Payments публикует результат, а статус заказа меняет только Orders. Только Orders публикует `OrderStatusChanged`, поэтому уведомления опираются на единую модель заказа.

## 2. Распределённая транзакция и отмена

Используется простая событийная saga, без отдельного сервиса-оркестратора. Orders владеет переходами заказа, Payments - платёжными операциями. В нормальном сценарии:

```text
PendingPayment -> Paid
PendingPayment -> PaymentFailed
PendingPayment -> Cancelled
Paid -> RefundPending -> Cancelled
```

`PaymentFailed` является финалом данной попытки в выбранном упрощённом сценарии; новая покупка оформляется новым заказом. Складских резервов и их компенсации нет: управление складом явно не входит в границы проекта.

При истечении срока оплаты Orders фиксирует отмену и публикует `OrderCancelled`. При отмене оплаченного заказа фиксирует `RefundPending` и тоже публикует `OrderCancelled` как факт принятой отмены с требованием возврата. После `RefundSucceeded` переводит заказ в `Cancelled`. Платёжные ошибки при возврате оставляют заказ в `RefundPending`; автоматические повторы ограничены, затем требуется операционное разбирательство.

Гонка «отмена одновременно с успешной оплатой» обрабатывается явно: Payments хранит намерение отмены независимо от порядка событий. Если деньги уже списаны или позднее приходит успешный webhook, инициирует идемпотентный возврат. Orders не переводит отменённый заказ в `Paid`; поздний `PaymentSucceeded` приводит к `RefundPending`, а не к исполнению заказа. Если `RefundSucceeded` доставлен раньше `PaymentSucceeded`, версия платёжного агрегата не позволяет устаревшему событию вернуть состояние назад.

Нельзя откатить внешний платёж SQL-транзакцией. Возврат является отдельной компенсирующей операцией, которая тоже может временно не пройти.

## 3. Доставка событий

| Механизм | Проектное правило |
| --- | --- |
| Transactional outbox | Изменение доменных данных и запись события фиксируются одной транзакцией в БД издателя; relay работает внутри развёртывания сервиса |
| Публикация | Relay отправляет persistent message в durable exchange/queue, ждёт publisher confirm и только затем отмечает запись отправленной |
| Семантика | At-least-once: повторная доставка возможна; exactly-once не обещается |
| Получение | Consumer пишет `event_id` в inbox и применяет изменение в одной транзакции; ACK отправляет после commit |
| Конверт | `event_id`, `event_type`, `schema_version`, `aggregate_id`, `aggregate_version`, `occurred_at`, `correlation_id`, `payload` |
| Очереди | Отдельная очередь на подписчика; несколько экземпляров одного сервиса конкурируют только внутри его очереди |
| Неупорядоченность | Полные снимки проекций применяются только с новой `aggregate_version`; для заказов и платежей дополнительно проверяются допустимые переходы |
| Повторы и DLQ | Временные ошибки повторяются с ограниченным exponential backoff, после лимита событие попадает в dead-letter queue; нужен алерт и контролируемый replay |
| Эволюция | Совместимые поля добавляются; ломающий формат получает новую версию контракта и переходный период |

Наличие inbox не делает внешний вызов exactly-once. Payments сначала сохраняет операцию со стабильным ключом и статусом `Preparing`, затем вызывает провайдера с тем же ключом. Если процесс упал после успешного списания, повтор/сверка находят ту же операцию, а не создают новое списание. Webhook может прийти раньше HTTP-ответа провайдера: сопоставление выполняется по стабильной merchant reference, записанной до вызова.

Для создания заказа ключ идемпотентности ограничивается пользователем и операцией; сохраняются хеш тела и результат. Повтор с тем же ключом и другим телом отклоняется. Для событий отмены до `OrderPlaced` Payments хранит отмену по `order_id`, чтобы запоздавшее создание не начало ненужную оплату.

## 4. Проекции и восстановление

**Feed.** Подписывается на карточки Catalog, интересы Users и статусы Orders. Продуктовые и пользовательские события содержат полную новую проекцию либо признак удаления. Для популярности Feed хранит вклад каждого заказа с версией: повтор события не удваивает продажи, возврат убирает вклад. Время учитывается по дате оплаты; агрегат за 30 дней обновляется с истечением окна.

**Notifications.** Хранит только необходимые контакты/согласия из Users. Уникальность задания задаётся `(order_id, order_version, channel)`. Если событие заказа пришло до контактной проекции, отправка откладывается и повторяется ограниченно; контакт не читается напрямую из Users DB. Старые статусы не должны вытеснять более новые в очереди доставки.

**Восстановление.** RabbitMQ не используется как бессрочный журнал для replay. В целевом развитии владельцы предоставляют контролируемый экспорт своих проекционных данных через API/задачу экспорта. При перестроении сначала включается накопление новых событий, затем загружается снимок, после чего применяются накопленные версии. Такая операция не даёт сервису прямого доступа к чужой БД. Эти административные API и процедуры сейчас не реализованы.

Контакты и согласия при изменении/удалении обновляются отдельным событием Users, подписки на него ограничены ACL. В Feed достаточно `user_id` и категорий; email, телефон и платёжные реквизиты ему не передаются.

## 5. Поведение при сбоях

| Сбой | Ожидаемое поведение |
| --- | --- |
| Catalog недоступен при оформлении | Orders не фиксирует заказ по недостоверной цене; клиент получает временную ошибку и может безопасно повторить запрос |
| RabbitMQ недоступен | Новые факты остаются в outbox; принятие заказа возможно, платёж и уведомления задерживаются; рост outbox требует мониторинга |
| Feed отстаёт от Catalog | Выдача временно устарела; финальная проверка каталога выполняется при оформлении |
| Таймаут создания платежа | Статус неизвестен, а не «неуспех»; Payments сверяется с провайдером по ID/ключу до новой попытки |
| Повтор webhook / сообщения | Проверяются ID, версия и идемпотентность; повтор не создаёт новую финансовую запись |
| Webhook не доставлен | Payments периодически сверяет незавершённые операции через API провайдера |
| Email/SMS-провайдер недоступен | Notifications сохраняет задание и повторяет отправку; статусы оплаты и заказа не откатываются |
| Сбой после фактической отправки уведомления | При поддержке провайдера применяется idempotency key; иначе редкий дубль возможен и это принятый компромисс |

Для будущей эксплуатации нужны корреляция HTTP-запросов и событий, метрики задержки очередей/outbox, число ошибок провайдеров, DLQ и возраст незавершённых платежей. Это требования к развитию, не уже настроенный мониторинг.

## 6. Health-check текущего каркаса

`GET /health` проверяет только доступность HTTP-процесса и возвращает `200 OK` с JSON. Зависимостей у каркаса нет, поэтому он не проверяет БД, RabbitMQ или провайдеров. После их появления следует разделить liveness процесса и readiness критичных зависимостей: недоступность email-провайдера не должна перезапускать сервис заказов.
